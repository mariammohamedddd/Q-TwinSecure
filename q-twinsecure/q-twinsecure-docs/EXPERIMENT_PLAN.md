# PoC Experiment Plan

## 1. Objective

Demonstrate how limited or interrupted software-emulated key supply can prevent establishment of a **new** protected connection epoch and how the resulting observation-delivery gap affects Digital Twin freshness.

## 2. Independent variables

Start with a small set of controllable parameters:

- Key pool capacity.
- Initial number of available keys.
- Key supply enabled/disabled.
- Time at which the active connection epoch is closed and a new one is requested.
- Sensor reading interval.
- Freshness thresholds.

Do not vary many parameters at once in the first demonstration.

## 3. Scenarios

### Scenario A — Normal operation
1. Enable key supply and populate the pool.
2. Establish a protected connection epoch.
3. Generate and transmit sensor readings.
4. Verify the Twin accepts readings and reports `CURRENT`.

Expected result: successful secure message delivery and fresh Twin observations.

### Scenario B — Key-supply interruption
1. Keep an established connection epoch active.
2. Interrupt new key generation.
3. Continue sending readings over the existing epoch.
4. Verify that the existing epoch remains active in the model.
5. Close/end that epoch and request a new one.
6. With no key available, verify that new connection establishment fails.
7. Stop delivery because there is no active protected epoch.
8. Observe the Twin transition to `DELAYED`, then `MISSING`, according to configured thresholds.

Expected result: interruption alone does not kill the established connection; lack of key material prevents a new epoch; the observation gap degrades freshness.

### Scenario C — Recovery
1. Resume key supply.
2. Replenish the key pool.
3. Request a new protected connection epoch.
4. Resume sensor transmission.
5. Verify the Twin returns to `CURRENT`.

Expected result: connection and observation delivery recover when key material becomes available again.

## 4. Measurements to record

| Metric | Meaning |
|---|---|
| `keys_generated` | Number of keys generated by the emulator |
| `keys_available` | Current number of available keys |
| `keys_consumed` | Number of keys allocated to connection epochs |
| `connection_state` | `CONNECTED` or `DISCONNECTED` |
| `connection_epoch` | Identifier for the active epoch |
| `readings_generated` | Sensor readings produced |
| `readings_delivered` | Readings accepted by the Twin |
| `last_observation_age` | Age of the latest valid observation |
| `twin_freshness` | `CURRENT`, `DELAYED`, or `MISSING` |

Never record raw key bytes or PSKs.

## 5. Expected observations

- Under normal conditions, key allocation succeeds and readings are delivered.
- During supply interruption, an already established connection remains usable in the simplified model.
- Once a new epoch is required, no available key means the new epoch cannot be established.
- If no readings arrive, observation age increases and freshness degrades.
- After key supply resumes and a key becomes available, a new epoch can be established and freshness recovers.

## 6. Interpretation limits

This experiment demonstrates behavior in a software model. It does not establish physical QKD security, production network performance, or the behavior of every TLS implementation. Clearly state the assumptions and simplifications in all reports.
